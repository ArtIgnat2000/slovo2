# Производительность — аудит и пакет A+B

2026-09-29 · `arena/01a0ec18-slovo2`

## Границы доказательств

Проверены исходники, production build и jsdom smoke. Браузерных трасс и замеров
на телефоне пользователя нет. Причина задержки **не установлена окончательно**.
Этот документ заменяет первоначальную редакцию: в ней гипотезы про SW и сеть
были ошибочно сформулированы как доказанные причины.

## Измеренный baseline до изменений

* 94 WebP, суммарно 376,2 KiB; среднее 4098 байт, максимум 9056 байт.
* Главный JS: 242128 байт, gzip локальной утилитой 79974 байта.
* CSS: 19861 байт, gzip 4700 байт.
* Precache: 110 записей, 753,17 KiB по отчёту VitePWA.
* Это размеры файлов, **не сетевой трафик и не время загрузки**. Иконки: 113,6 KiB.

## Находки

| Область | Подтверждено кодом | Вывод / следующий шаг |
|---|---|---|
| Картинка карточки | URL обнаруживается при монтировании, нет прогрева; async decode; размер зарезервирован | Позднее обнаружение и декодирование могут давать заметную паузу даже с кэшем |
| Отказ загрузки | Не было обработчика ошибки или подложки | Теперь эмодзи до загрузки и при ошибке |
| Словарик | До 94 eager-миниатюр одновременно | Lazy только для миниатюр; текущая карточка не lazy |
| SW | immediate registration, полный precache | Возможна конкуренция за сеть на первом визите; waterfall не снят. Не доказано, что SW блокирует именно эту картинку |
| Хранилище | Весь Zustand state сериализуется на set, в том числе toast; answer и XP — разные set; openDB вызывается на каждую операцию | Профилировать длинную историю; затем atomic answer+XP, partialize transient state, reuse DB connection. Не вводить debounce без тестов потери данных |
| Запуск | render ждёт rehydrate, persist также имеет автоматическую гидратацию | Проверить двойное чтение; добавить статический splash и один согласованный путь гидратации, не разрешая запись поверх ещё не загруженного профиля |
| React | App и Lesson подписаны на весь активный профиль; настроение меняет App | Это потенциальные лишние рендеры, не доказательство лагов. Профилировать, не memo всё подряд |
| CSS | blur на диалогах, постоянные анимации, width-анимация полоски | Проверить слабый GPU; reduced-motion, transform где оправдано |
| Таймеры | В TaskView есть callback после задержки без cleanup | Риск ответа после выхода; устранить перед учётом сессий в адаптации |
| Обновления | autoUpdate сочетается с UI ручного обновления | Проверить обновление во время урока; без checkpoint внезапный reload особенно нежелателен |

Размер изображений уже разумный. Полный precache меньше 1 MiB: удалять его ради
скорости без измерений не стоит. Cache Storage хранит байты, а не гарантированно
декодированные пиксели. Повторный визит не гарантирует отсутствие задержки.
Заголовки GitHub Pages и доступность сети пользователя здесь не измерены;
утверждения про max-age=600 и блокировку github.io не используются как диагноз.

## Варианты и выбор

* **A (выбран):** эмодзи-подложка, мягкое появление картинки, высокий приоритет
  текущей карточки; lazy и низкий приоритет миниатюр. Подложка улучшает восприятие,
  но сама не ускоряет сеть.
* **B (выбран):** best-effort прогрев ближайшего урока на главной и следующих трёх
  карточек внутри урока, включая repair. Idle callback с fallback; отмена при
  смене экрана, уважение Save-Data; не более 16 удерживаемых Image объектов.
* **C (не выбран):** эксперимент с регистрацией SW после load. Не гарантирует
  устранения конкуренции при SPA-переходах; откладывает готовность офлайна.
  Runtime-only картинки меняют офлайн-контракт, поэтому сейчас не нужны.
* **D (не выбран):** сравнить сети/хостинги с телефона, только затем обсуждать зеркало.
  Перенос origin требует экспорта прогресса: IndexedDB старого сайта не переедет сама.

Реализованы только A+B. Precache и политика SW не изменены. Никаких новых
зависимостей, телеметрии или аудиозапросов. Прогрев не гарантирует готовности:
idle callback может не успеть, браузер может освободить декодированные данные.

## Экспертное ревью и первичные источники

Проведена отдельная консультация экспертной модели: подход к картинкам признан
соразмерным; подтверждены блокеры адаптации — ошибки Build и точный контракт
однократного учёта выхода/завершения. Это ревью кода/проекта, не замена браузерным
измерениям.

* Раннее обнаружение и приоритет ключевого изображения, без lazy для него:
  [1](https://developer.chrome.com/docs/performance/insights/lcp-discovery).
* Lazy для некритичных изображений, width/height для геометрии:
  [2](https://web.dev/learn/images/performance-issues).
* Возможная конкуренция установки SW за сеть, выбор времени регистрации:
  [3](https://web.dev/articles/service-workers-registration).
* Runtime Image CacheFirst — возможная стратегия, не обязательная замена precache:
  [4](https://developer.chrome.com/docs/workbox/modules/workbox-recipes).

## Проверки и критерии приёмки

Автотесты: placeholder до load, load открывает изображение, error оставляет эмодзи,
приоритеты и lazy; существующие сценарии уроков/магазина/первого запуска.
jsdom не проверяет сеть, декодирование, анимацию или SW.

На production-сборке с base `/slovo2/` проверить на Android Chrome и iOS Safari:
1. Холодный визит, установленный SW, повторный визит, авиарежим после установки.
2. Медленная сеть (например 1,6 Mbps/150 ms RTT), 4× CPU; при эмуляции отдельно
   проверить, что ограничения распространяются и на SW target.
3. Главная → первый урок, следующие карточки, repair, словарик → карточка,
   ошибка/404 картинки, Save-Data, быстрый выход, обновление во время урока.
4. Записать tap→карточка и tap→готовая картинка отдельно; p50/p95 по повторным
   прогонам, сетевой waterfall, long tasks. LCP не заменяет метрику SPA-перехода.
5. Цель: ни одной пустой области при сбое изображения, никакого роста задержки
   тапа; затем согласовать численный бюджет по baseline телефона.

Не заявляем измеренного ускорения до этих проверок.
