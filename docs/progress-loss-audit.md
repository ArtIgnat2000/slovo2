# Аудит: почему мог пропасть прогресс (2026-10-03)

Повод: у одного из тестировщиков (ребёнок) «внезапно пропал весь прогресс».
Как это произошло — неизвестно. Задача этого документа: разобрать хранение
прогресса по косточкам, перечислить все каналы потери, которые реально открыты
в коде, оценить их правдоподобность для такого случая и предложить защиту.

**Состояние:** аудит сделан на `main` (`66714b3`, v0.9.0); затем по его итогам
защита P0–P2 внедрена в этой же ветке — см. §7 «Что сделано по итогам аудита».
Всё, что описано в §0–§4, — разбор исходной ситуации; §5 план; §6 стенд.

---

## 0. Короткий ответ

1. **Восстановить неоткуда.** Прогресс живёт только в браузере ребёнка: одна
   запись в IndexedDB, ни сервера, ни аккаунта, ни автоматической копии. Это
   осознанное свойство продукта («данные остаются в телефоне»), но у него есть
   цена: любое стирание записи — окончательное.
2. **Само приложение прогресс не обнуляет.** Ни один участок кода не сбрасывает
   профиль автоматически: `resetProfile`, `deleteProfile` и `replaceAll`
   вызываются только по явному действию пользователя (`src/ui/screens/ParentScreen.tsx:77,274`,
   `src/ui/screens/ProfilesScreen.tsx:112`). Сбоя «логика обнулила профиль» нет.
3. **Зато открыты восемь каналов потери**, и ни один не оставляет следа:
   нет журнала, нет резервной копии, пользователю не сообщается ничего.
   Все восемь подтверждены прогоном на настоящем сторе (§2).
4. **Самое правдоподобное для «ребёнок, данных нет»:**
   * ребёнок сам удалил/сбросил профиль — путь до кнопок короткий, а
     «родительский» гейт — пример на таблицу умножения второго класса
     (`ParentScreen.tsx:21`), то есть не преграда для целевой аудитории;
   * браузер почистил хранилище сам (у WebKit это 7 дней без взаимодействия
     с сайтом, если приложение не добавлено на экран —
     [WebKit Tracking Prevention][webkit-itp], [обзор][selfstore]);
   * приложение один раз стартовало «пустым» (хранилище не прочиталось),
     ребёнок создал профиль — и пустое состояние перезаписало старую запись;
   * **ложная потеря**: ребёнок (или брат) создал второй профиль, активным стал
     пустой, старый профиль цел и просто не выбран.

## 1. Как устроено хранение сейчас

```
zustand persist (src/state/store.ts:494-501)
   name: 'slovo2', version: 1, partialize → { profiles, activeId, settings }
        ↓ JSON
idbStorage (src/platform/storage.ts:27-41)
        ↓ idb
IndexedDB: БД «slovo2» → store «kv» → ключ «slovo2»
```

* **Одна запись на всё.** Нет ни истории, ни снимков, ни корзины: в базе ровно
  один ключ (проверено стендом, сценарий 7).
* **Пишется целиком на каждое изменение состояния.** Любой `set` — ответ в
  уроке, показ тоста, переключение звука — сериализует и кладёт в базу весь
  снимок всех профилей. Объём маленький: **10,4 КБ** за 365 дней занятий и все
  94 слова (сценарий 10) — квота тут ни при чём, но именно поэтому запись так
  легко перезаписать целиком.
* **Читается один раз при старте**: `await useApp.persist.rehydrate()` в
  `src/main.tsx:12`. try/catch вокруг него комментируется как «первый запуск —
  базы ещё нет», но на практике **не срабатывает никогда**: `persist` внутри
  `hydrate()` сам глушит ошибку (см. ниже).
* **Нет ни одной из штатных страховок zustand:**
  * `migrate` не задан — при расхождении версии схема «теряется» (§2, сцен. 3);
  * `onRehydrateStorage` не задан — ошибка чтения уходит в никуда;
  * `merge` по умолчанию — shallow, данные не проверяются;
  * `skipHydration` не задан — при импорте модуля hydration стартует сам,
    дополнительно к awaited-вызову в `main.tsx`.
* **Валидация есть, но не там.** `normalizeProfile()` (store.ts:100) применяется
  только в `replaceAll` (импорт файла). При чтении из базы профили
  **не нормализуются** — запись попадает в состояние как есть.
* **Кросс-вкладочной синхронизации нет**: ни `BroadcastChannel`, ни Web Locks,
  ни ре-гидрации по `visibilitychange` (grep по `src/` — пусто).
* **`navigator.storage.persist()` вызывается один раз при старте**
  (`main.tsx:24`), результат никому не показывается и нигде не проверяется.
  На iOS Safari StorageManager доступен [с версии 17][caniuse-storage], а
  действенную защиту даёт именно [установка приложения на экран][webkit-itp] —
  про это в приложении сказано только мимоходом в баннере.

## 2. Подтверждённые каналы потери

Стенд: `npm ci && npm run audit:storage` (`scripts/audit-storage.mjs` +
`tests/storage-audit.probe.tsx`). Он работает с настоящим стором в jsdom +
fake-indexeddb и задаёт хранилищу жизненные ситуации. Вывод от 2026-10-03:

| № | Канал | Что видит человек | Итог |
|---|---|---|---|
| 1 | *Контроль: обычный старт читает прогресс* | — | ☑ чтение работает, профиль с XP 500 на месте |
| 2 | **Битая запись** (оборванная запись, сбой флеша, «уборка» браузера) | «Пока нет ни одного ученика» | ☒ тихий пустой старт → первое действие стирает прошлое |
| 3 | **Расхождение версии схемы** без `migrate()` | то же | ☒ `console.error` + `TypeError` внутри `persist`, промис не падает → пустой старт → стирание |
| 4 | **Хранилище недоступно на старте** (приватный режим, чистка iOS, блокировка, диск заполнен) | то же | ☒ `rehydrate()` не выбрасывает исключение вообще → пустой старт → стирание |
| 5 | **Запись не удалась** (квота, отказ браузера, хранилище вычищено в фоне) | «успех» — в памяти всё начислено | ☒ непойманное отклонение промиса, в базе осталось старое; всё начисленное после сбоя теряется при перезапуске |
| 6 | **Вторая вкладка / фоновая копия приложения** | ничего | ☒ устаревший слепок затирает свежий прогресс (2 профиля → 1) |
| 7 | **Удаление профиля** (аватар в шапке → 🗑 → «Удалить профиль», гейта нет) | подтверждение, где безопасная кнопка — главная | ☒ безвозвратно: ключей в базе 1, корзины нет |
| 8 | **Импорт файла** с неполными данными | «Не удалось загрузить файл» — или ничего | ☒ невалидные профили отбрасываются молча, старая запись затирается сразу |
| 9 | *Ложная потеря:* создан второй профиль | «Уровень 1, освоено 0 из 94» | ☑ данные целы, активный профиль переключился |
| 10 | *Справка:* объём записи — 10,4 КБ/год | — | квота не причина |

### Ключевая механика: «пустой старт стирает данные»

Сценарии 2–4 разные по причине, но одинаковы по последствиям:

1. `hydrate()` внутри zustand глушит **любую** ошибку чтения — она уходит
   только в `onRehydrateStorage`, которого у нас нет
   (`node_modules/zustand/esm/middleware.mjs:433-438`). Промис `rehydrate()`
   при этом **успешно** завершается, поэтому `try/catch` в `main.tsx` не
   срабатывает.
2. Приложение рендерит экран профилей с надписью «Пока нет ни одного
   ученика» — как при первом запуске.
3. Любое следующее действие (создать профиль, переключить звук) пишет в базу
   `{profiles: [], …}` → **старая запись уничтожена безвозвратно**.

То есть *единичный* сбой чтения превращается в *полную* потерю — именно потому,
что пустое состояние ничем не отличается от «первого запуска» и нигде не
проверяется перед записью.

### Отдельно: мина на будущее

`version: 1` и отсутствие `migrate()`. Сейчас это безвредно, но **любое**
повышение версии схемы без `migrate` = пустой старт у всех пользователей и
мгновенное стирание их прогресса (сценарий 3). До первого повышения версии
нужно обязательно добавить `migrate` — это дешёвая страховка.

## 3. Что причиной НЕ является (проверено и снято)

* **Автоматический сброс в коде.** grep по `resetProfile`/`deleteProfile`/
  `replaceAll`/`clearStorage`: вызовы только из обработчиков кнопок.
* **Квота/переполнение.** Запись ~10 КБ за год против сотен мегабайт квоты.
* **Обновление приложения и PWA.** `registerType: 'prompt'` — страница сама не
  перезагружается; `cleanupOutdatedCaches` чистит кеши сервис-воркера, а не
  IndexedDB; выгрузка новой версии на Pages хранилище не трогает.
* **Переезд сайта на другой адрес** — адрес постоянен
  (`https://artignat2000.github.io/slovo2/`, CNAME в репозитории нет). Но если
  ребёнок заходил по ссылке из мессенджера, открытой во встроенном браузере
  (ВК/Telegram), это **другой контейнер хранения**: прогресс, начатый там, не
  виден в Safari и наоборот. То же самое про Safari против ярлыка на экране.

## 4. Как разобрать конкретный случай (анкета для родителей)

Никаких следов в приложении нет, поэтому остаётся расспрос. Ответы прямо
указывают на канал:

| Вопрос | Ответ → что это значит |
|---|---|
| Список профилей сейчас пустой («Пока нет ни одного ученика») или имя ребёнка в списке есть? | Имя есть → данные целы (ложная потеря, сцен. 9) либо сброшен именно профиль. Список пуст → настоящее стирание (сцен. 2–4, 7). |
| Имя ребёнка в списке одно или их несколько? | Несколько → почти наверняка создан второй профиль и он активен (сцен. 9). Прогресс вернётся переключением обратно. |
| Приложение открывали с ярлыка на экране или через Safari/Chrome? Не менялся ли способ на днях? | Сменился → другой контейнер хранения, старые данные лежат в прежнем. |
| Был ли перерыв в занятиях больше недели? Приложение добавлено на экран телефона? | Перерыв >7 дней и нет ярлыка → [чистка WebKit][webkit-itp] (сцен. 4). |
| Ребёнок пользовался телефоном один? Был ли разблокирован раздел «Родителям»? | Да → удаление профиля (сцен. 7), сброс прогресса или импорт файла (сцен. 8). |
| Сохраняли ли файл выгрузки («Родителям → Прогресс → Сохранить»)? | Если да — прогресс восстанавливается кнопкой «Загрузить». |
| Были ли открыты две копии приложения (вкладка в браузере и ярлык)? | Да → сцен. 6. |
| Какая версия в «Настройках → Версия»? | Сверяем с git: понимаем, та ли сборка. |

**Что можно попробовать прямо сейчас:** открыть приложение тем же способом,
что и раньше (тот же ярлык/браузер) → в шапке нажать аватар → посмотреть
список профилей → переключиться на профиль ребёнка. Если профиль там есть —
ничего не пропадало. Если список пуст — данные стёрты, вернуть их можно только
из файла выгрузи.

**Вывод по этому случаю:** без файла-выгрузки прогресс не восстановить, и это
само по себе — главный вывод аудита. Дальше имеет смысл не гадать, а сделать
так, чтобы (а) следующий случай оставлял следы и (б) большинство каналов было
закрыто.

## 5. Предложения: как не допускать повторения

Принципы продукта не затрагиваются: всё так же офлайн, без сервера, без
аккаунтов и без аналитики. Меняется только то, как приложение обращается с
данными на устройстве.

### P0 — «не давать пустому стирать полное» (≈2–3 часа, закрывает сцен. 2, 3, 4, 5)

1. **Ловить ошибки гидрации.** Добавить `onRehydrateStorage`: при ошибке
   поднимать флаг `storage: 'error'` и показывать вместо экрана профилей
   понятный экран «Не удалось открыть сохранённый прогресс» с кнопками
   «Попробовать снова» / «Загрузить резервную копию» / «Начать заново».
   Пустой экран «создайте первый профиль» — недопустимый ответ на сбой чтения.
2. **Запрет записи «пустого поверх полного».** Перед каждым `setItem`
   сверяться: если в памяти профилей нет, а в хранилище есть, — не писать, пока
   пользователь явно не выбрал «Начать заново». Одна эта проверка превращает
   сценарии 2–4 из «полная потеря» в «ничего не произошло».
3. **`migrate()` + тест** на несовпадение версии (сцен. 3). Обязательное
   условие для любого будущего изменения схемы.
4. **Обработка ошибок записи.** Обернуть `setItem`: при неудаче — флаг
   «сохранение не удалось» и видимый баннер («Прогресс не сохранился,
   попробуй ещё раз»), а не непойманный промис. Плюс `lastWriteAt` в состоянии.

### P1 — снимки и корзина (≈4–6 часов, закрывает сцен. 7, 8 и последствия остальных)

5. **Ротация снимков.** Ключи `slovo2` (текущий) + `slovo2~1…~3` (предыдущие,
   с датой, числом профилей и суммой XP). Новый снимок пишется поверх самого
   старого; в «Родителям → Прогресс» — список «Вернуть как было: вчера /
   3 дня назад» с предпросмотром. Для записи в 10 КБ это бесплатно.
6. **Мягкое удаление.** `deleteProfile` и `resetProfile` переносят профиль в
   корзину на 30 дней + 10-секундное окно «Отменить». Путь ребёнка к 🗑
   перекрывается: из шапки открывается только *переключение* профиля, а
   удаление переносится в родительский раздел.
7. **Честный импорт.** Перед `replaceAll` показывать сводку: «В файле: 1
   профиль, 12 освоенных слов, выгрузка от 12.09. Сейчас: 2 профиля, 40 слов.
   Заменить?» + обязательное подтверждение словом. Если часть профилей
   невалидна — сообщать об этом явно, а не молча выбрасывать.
8. **Усиление родительского гейта.** Пример `2×2…9×9` решается второклассником
   (и перебирается: `a` и `b` стабильны в рамках монтирования). Варианты:
   четырёхзначный родительский ПИН, задаваемый при первом входе, или задача
   уровня «37 × 8» + удержание кнопки. Любой из них — отдельное согласование.

### P2 — устойчивость окружения (≈6–10 часов, закрывает сцен. 6 и «чистку»)

9. **Постоянное хранилище по жесту.** `requestPersistence()` вызывать по
   нажатию (в «Родителям → Прогресс») и показывать статус: «Защита от очистки:
   включена / не включена — добавьте приложение на экран». Для iOS именно
   установка на экран снимает 7-дневную чистку WebKit.
10. **Несколько копий приложения.** `BroadcastChannel` + ре-гидрация по
    `visibilitychange`, либо Web Locks с единственным писателем; минимум —
    сверка ревизии перед записью, чтобы устаревшая вкладка не затирала свежую.
11. **Местный журнал** (без сети): последние ~20 событий — старт, гидрация
    ok/ошибка, запись ok/ошибка, удаление, сброс, импорт, с датой и версией
    сборки. Экран «Родителям → Прогресс → Журнал». Это и есть ответ на вопрос
    «нет данных, как это произошло» в следующий раз.
12. **Напоминание о выгрузке**: если экспорта не было больше 14 дней — мягкий
    баннер родителю с кнопкой «Сохранить файл».
13. **Диагностический экран** (например, по `?diag=1`): доступность IndexedDB,
    размер записи, даты снимков, статус `persisted()`, версия сборки. Нужен
    и для разбора этого случая, если найдётся второй телефон с симптомами.

### P3 — процесс

14. Превратить стенд из §6 в регрессионный тест: после P0/P1 сценарии 2–8
    должны **не** стирать данные — и тогда он идёт в CI рядом с `test:smoke`.
15. Анкету из §4 положить в README (раздел для родителей/поддержки), чтобы
    следующий случай начинался со сбора фактов.
16. Перед релизом — ручная проверка на iOS и Android по чек-листу: установить
    на экран, убить приложение, открыть две копии, не заходить 8 дней.

### Побочная находка (не про хранилище)

`npm run test:smoke` на текущем HEAD стабильно падает на одной проверке:
«задания дня: награда за задание забрана». Причина — в самом тесте:
`btnText('Забрать')` берёт **первую** кнопку на странице, а не кнопку в
карточке «Повтори»; при текущем порядке заданий клик попадает в карточку
«6 верных ответов подряд» (`claimed=["2026-10-03:flawless"]`). Продукт работает
верно. Лечится поиском кнопки внутри нужной `.quest` — предлагаю сделать
отдельной правкой, чтобы CI-деплой не висел на хрупкой проверке.

## 7. Что сделано по итогам аудита (2026-10-03)

Внедрены P0, P1 и P2 (план — §5). Ничего из стоп-листа проекта не затронуто:
как и раньше, всё офлайн, без сервера, аккаунтов и аналитики.

**P0 — «пустое не стирает полное»**

* `src/platform/vault.ts` — сторож записи `createGuardedStorage`:
  * пока сохранение не прочитано, запись **заморожена** (`src/state/health.ts`,
    `frozen`): пустой старт больше не затирает старую запись;
  * перед перезаписью снимает копию прежней записи, если новое состояние
    «беднее» (меньше профилей/XP/слов) или прежнее не читается;
  * ошибки записи не уходят в никуда: статус `write-error` + баннер
    «прогресс не сохраняется» + запись в журнале;
  * **записи выстроены в очередь**: иначе две быстрые записи читали бы одно
    и то же состояние, и вторая затирала бы правки первой.
* `merge`/`migrate` в `persist`: сохранённое состояние проходит санитайзер,
  невалидный профиль не выбрасывается, а уходит в корзину; расхождение версии
  больше не означает потерю.
* `src/ui/StorageScreen.tsx` — экран «Прогресс не удалось открыть» вместо
  молчаливого «создайте первого ученика»: «Попробовать снова», «Загрузить
  копию из файла», «Вернуть как было», осознанное «Начать заново».

**P1 — снимки и корзина**

* Копии `slovo2.snap.1…3` (кольцо, не чаще раза в 30 минут) + кнопка
  «Вернуть как было» с датой и числом профилей; восстановление само снимает
  копию — то есть отменяемо.
* `deleteProfile` и `resetProfile` складывают профиль в корзину на 30 дней;
  «Родителям → Прогресс» показывает их и возвращает целиком.
* Импорт: прежние профили уходят в корзину, в подтверждении показывается,
  сколько профилей было и сколько станет.
* Удаление профиля убрано с детского пути: из аватара в шапке открывается
  только переключение ученика (`manage` — только из раздела «Родителям»).

**P2 — окружение**

* `BroadcastChannel` + ре-гидрация на возврате в фокус: вторая копия приложения
  не затирает свежий прогресс (во время урока не трогаем ничего).
* Статус постоянного хранилища виден родителю, включается по кнопке (нужен
  жест пользователя), рядом — объяснение про ярлык на экране.
* Журнал событий (старт, чтение, запись, удаление, сброс, импорт) в «Родителям».
* Напоминание сделать копию файла, если выгрузки не было больше 14 дней.

**Побочно найденное и исправленное**

* `persist` оборачивает `setState` и пишет в базу **на каждый вызов**, даже
  когда состояние не изменилось — из-за этого «записать в журнал, что запись
  не удалась» уходило в бесконечный цикл. Обход: править состояние только при
  реальном изменении.
* `npm run test:boot` был зелёным при **сломанной** IndexedDB в своём
  окружении (не хватало IDB-глобалей, а ошибка чтения глоталась). Окружение
  починено, и добавлен второй прогон: при недоступном хранилище приложение
  обязано показать экран сбоя, а не «первый запуск».
* `tests/quests-ui.test.tsx`: кнопка «Забрать» искалась по всей странице и
  попадала в чужое задание — проверка падала на работающем продукте. Теперь
  ищется внутри карточки нужного задания.
