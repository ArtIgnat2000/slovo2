## 1. Коротко

Сейчас приложение — тренажёр **одного** пака: 94 словарных слова 2 класса,
16 уроков-тем. Предлагается сделать класс **свойством профиля**, а слова —
**общим банком 1–4 классов**:

* в профиле появляется `activeClass: 1 | 2 | 3 | 4`;
* главная, «Мой путь», словарик, «Родителям → Обзор» показывают выбранный класс;
* у слова **одна карточка и один прогресс** на все классы, у урока — свой `grade`;
* смена класса меняет **только** `activeClass` (и сбрасывает адаптивное окно);
  опыт, кристаллы, серия, заморозки, достижения, дни, история занятий,
  уровни уроков, покупки, тюнинг, музыка, звуки, мечты, пазлы, облик сундука,
  недельные и дневные награды **не трогаются**;
* существующие профили продолжают открываться во 2 классе — для них ничего
  не меняется;
* повторение остаётся по **всем изученным** словам (как сейчас): это защищает
  межклассовое повторение и не ломает план заданий дня.

Что нашли по учебникам (подробно — в приложении):

| Класс | Слов в словарике | Новых карточек | Уроков (предложение) |
|---:|---:|---:|---:|
| 1 | 30 | 2 (`лисица`, `мальчик`) | 5 |
| 2 | 94 (текущий пакет) | 0 | 16 (без изменений) |
| 3 | 72 | 71 | 13 |
| 4 | 94 | 93 | 15 |
| **Всего** | **257 уникальных** | **163** | **49** |

Точность — **±3 слова**: подборки расходятся на 1–3 единицы, окончательный
список фиксируется по печатному словарику (§2.2).

Главная работа — не код, а **163 новые карточки** (ударение, слоги, опасные
буквы, эмодзи, предложение, подсказка, мнемоника) и вычитка словарей.
Поэтому предлагаю выпускать поэтапно: сначала механику и 1 класс, затем 3-й,
затем 4-й (см. §11).

## 3. Главное решение: один банк слов, класс — это фильтр

### 3.1. Почему не четыре отдельных пака

Словарики классов почти не пересекаются: 28 слов из 30 в 1 классе уже есть
в пакете 2 класса, а 3 и 4 классы почти целиком состоят из новых слов.
Общие слова всё же есть — «обед» (2 и 3 класс), «тарелка» (2 и 4),
«грамм», «килограмм» и «интересно» (3 и 4). Если завести четыре независимых
пака, у них будут разные `id`:

* прогресс по «обед» из 2 класса не увидит 3 класс;
* при возврате в прошлый класс часть слов «познакомится» заново;
* одну карточку придётся поддерживать в двух местах;
* картинки и мнемоники начнут расходиться.

Поэтому — **один банк `WORDS`**, у слова есть `grades: ClassId[]`,
а у урока — `grade`. Слово живёт в банке один раз, уроки ссылаются на его `id`.

### 3.2. Что это даёт ребёнку

* Переход из 2 в 3 класс не сбрасывает прогресс: уровни уроков, освоенность
  слов, интервалы повторения и вся коллекция остаются.
* Слова, общие для двух классов, узнаются сразу: в 3 классе «обед» уже
  знаком, в 4-м знакомы «тарелка», «грамм» и «килограмм».
* Вернулся в прошлый класс — всё на месте, включая уровни уроков.
* Слова из прошлых классов продолжают приходить в «Повторение».
* Смена класса не выглядит как «начать заново»: это переключение программы.
* Знакомые слова не проходят «знакомство» заново: `buildLesson` показывает
  `intro` только словам, у которых ещё нет ни одного ответа
  (`ok + wrong === 0`) — общий прогресс это уже обеспечивает.

### 3.3. Что считается «классом»

**Активный класс** — это программа, которую ребёнок проходит сейчас:
какие уроки на «Моём пути», какой словарик открывается по умолчанию,
что показывать в «Родителям → Обзор» как «программа класса».

Класс **не** влияет на экономику, награды, пазлы, магазин, сундуки,
достижения и ранги БУКа.

## 4. Модель данных

### 4.1. `src/types.ts`

```ts
export type ClassId = 1 | 2 | 3 | 4;

export interface Word {
  id: string;
  text: string;
  stress: number;
  syllables: string[];
  danger: number[];
  dangerKind: DangerKind;
  hint: string;
  emoji: string;
  sentence: string;
  mnemonic?: string;
  image?: string;
  theme: string;
  /** Классы, в словарике которых встречается слово. Одна карточка на все классы. */
  grades: ClassId[];
}

export interface Lesson {
  id: string;
  title: string;
  emoji: string;
  /** Порядок внутри своего класса */
  order: number;
  wordIds: string[];
}

/** Урок программы класса. «Повторение» (REVIEW) остаётся просто Lesson. */
export interface GradeLesson extends Lesson {
  grade: ClassId;
  /** Необязательная часть учебника — для длинного «Моего пути» (позже) */
  part?: 1 | 2;
}

export interface Profile {
  // …
  /** Программа, которую ребёнок проходит сейчас. Старые профили → 2. */
  activeClass: ClassId;
}
```

`WordState`, `LessonState`, `days`, `shop`, `puzzle`, `daily`, `weekly` **не
меняются**: прогресс уже ключуется глобальными `wordId` / `lessonId`.

### 4.2. Идентификаторы слов — не ломаем существующие

Сейчас `id = g2_<текст>`. Менять схему нельзя: `profile.words` уже хранит
ключи `g2_Москва`, `g2_класс` и т. д. Предлагаю правило:

```ts
// Если слово входит в программу 2 класса — исторический префикс g2_ сохраняется.
// Иначе — префикс первого класса, в котором слово появляется.
const gradePrefix = grades.includes(2) ? 2 : Math.min(...grades);
const id = `g${gradePrefix}_${text}`;
```

Проверка на текущих данных: все 94 слова входят в 2 класс → получают
ровно те же `id`, что и сейчас. «лисица» (`[1]`) → `g1_лисица`,
«понедельник» (`[3]`) → `g3_понедельник`, «килограмм» (`[3, 4]`) →
`g3_килограмм`, «библиотека» (`[4]`) → `g4_библиотека`.

Префикс — **историческое имя, а не фильтр класса**. Это нужно явно написать
в комментарии к парсеру, иначе следующий разработчик решит, что `g2_` значит
«только 2 класс».

### 4.3. Уроки

* Существующие 16 уроков получают `grade: 2`, их `id` **не меняются**
  (`school`, `birds`, …): в `profile.lessons` уже лежат эти ключи.
* Новые уроки: `g1_school`, `g3_school`, `g4_library` и т. д. —
  префикс класса защищает от коллизий с историческими `id`.
* `REVIEW` остаётся один на всё приложение (`id: 'review'`), без `grade`:
  повторение собирается из всех изученных слов. Поэтому `grade` живёт
  в `GradeLesson`, а не в `Lesson`: «Повторение» не притворяется уроком
  какого-то класса, и все функции, которые сегодня принимают `Lesson`
  (`buildLesson`, `LessonScreen`), менять не нужно.

## 5. Контент-слой `src/content/words.ts`

### 5.1. Где хранить классы

**Формат RAW не меняем.** 94 строки успешного пака остаются байт-в-байт:
у них и так есть все поля, а любая правка 94 строк — лишний риск. Классы
живут в отдельной карте, как уже сделано с темами (`THEME_OF`):

```ts
const GRADES_OF: Record<string, ClassId[]> = {
  // 94 существующих слова
  Москва: [1, 2],
  обед: [2, 3],
  тарелка: [2, 4],
  // новые
  лисица: [1],
  понедельник: [3],
  килограмм: [3, 4],
  библиотека: [4],
};

// новые строки — как обычные строки пака; картинка по-прежнему необязательна
// понедельник|5|по-не-дель-ник|1,3|vowel|📅|____ — первый день недели.|день после воскресенья|||
// библиотека|...|📚|...|hint|||
```

В `parse()` это выглядит так:

```ts
const grades = GRADES_OF[text];
if (!grades?.length) throw new Error(`Нет класса для «${text}» в GRADES_OF`);
const prefix = grades.includes(2) ? 2 : Math.min(...grades);
out.push({ id: `g${prefix}_${text}`, /* … */ grades });
```

Почему карта, а не 11-е поле:

* **нулевой diff в существующем контенте**: 94 проверенные строки не
  трогаются, релиз 0.27.0 не может случайно испортить слова 2 класса;
* `check-content.mjs` продолжает разбирать 9–10 полей — меньше правок
  в самом строгом валидаторе;
* `THEME_OF` уже задаёт такой стиль, карта читается привычно;
* ошибка «слово есть в RAW, но без класса» ловится проверкой покрытия
  (см. §9.2), а не молчаливым `?? []`.

Новые слова без картинки пишутся с пустым 10-м полем — это формат уже
поддерживает (`image` необязателен).

### 5.2. Экспорты

```ts
export const CLASS_IDS: ClassId[] = [1, 2, 3, 4];
export const CLASS_META: Record<ClassId, {
  title: string;      // «1 класс»

  accent: string;     // цвет карточки в выборе класса

export const WORDS: Word[];                       // весь банк

export const LESSONS_BY_GRADE: Record<ClassId, GradeLesson[]>;
export const LESSONS: GradeLesson[];              // все, по классам и order

```

`AVAILABLE_CLASSES` вычисляется по непустым `LESSONS_BY_GRADE` — это
избавляет от ручного флага «класс готов/не готов» и позволяет выпускать
1–2 классы раньше, чем 3–4.

### 5.3. Тема и урок

Сейчас у слова **одно** поле `theme`, и уроки собираются через
`byTheme(theme)`, а словарик фильтрует как `w.theme === lessonFilter`.
Для одного класса это работает. Для четырёх — нет: «молоко» входит в пакет
1 класса и в пакет 2 класса, и один `theme` не может указывать на два разных
урока. Поэтому:

* источник правды «где учим слово» — **`Lesson.wordIds`**;
* `WordsScreen` фильтрует по `wordIds` выбранного урока, а не по `theme`;
* поле `theme` остаётся у слова только для обратной совместимости и как
  подсказка при добавлении новых слов (`theme` = `id` первого урока,
  в котором слово появляется); в новых классах оно не участвует в логике.

Уроки собираются явными массивами с проверкой на месте:

```ts
const lesson = (
  grade: ClassId, id: string, title: string, emoji: string, order: number, words: string[],
): GradeLesson => ({
  id, grade, title, emoji, order,
  wordIds: words.map((text) => {
    const word = WORDS.find((w) => w.text === text);
    if (!word) throw new Error(`Урок ${id}: нет слова «${text}»`);
    if (!word.grades.includes(grade)) throw new Error(`«${text}» не входит в ${grade} класс`);
    return word.id;
  }),
});
```

Существующие 16 уроков 2 класса **остаются на `byTheme`** — их данные
не трогаем, они лишь получают `grade: 2`. Новые классы — через `lesson(...)`.

Чтобы `theme` оставался осмысленным для новых слов (он ещё используется
в `CardDemo` и как подсказка при вычитке), после сборки уроков делаем
один проход:

```ts
const firstLesson = new Map<string, string>();
for (const l of LESSONS) {
  for (const id of l.wordIds) if (!firstLesson.has(id)) firstLesson.set(id, l.id);
}
for (const w of WORDS) {
  if (!THEME_OF[w.text]) w.theme = firstLesson.get(w.id) ?? w.theme;
}
```

Тогда у каждого нового слова `theme` = id первого урока, где оно
встречается, а старые 94 сохраняют свои темы.

Ошибка в слове должна падать **на импорте контента**, а не в уроке у ребёнка.

## 6. Стор и миграция

### 6.1. Новый профиль и создание

```ts
function newProfile(name: string, avatar: string, classId: ClassId = 2): Profile {
  return { /* … */ activeClass: classId };
}

createProfile: (name: string, avatar: string, classId: ClassId = 2) => void;
```

Дефолт `2` оставляем не для UI (там класс выбирается явно), а чтобы
существующие тесты и демо-макеты продолжали компилироваться без правок.

`setProfileClass(id, classId)` — сменить класс у любого профиля
(нужно экрану «Профили», где можно редактировать другого ученика);
он так же сбрасывает `adaptiveGood`, как и `setActiveClass`.
`setActiveClass(classId)` — обёртка для активного профиля.

### 6.2. Смена класса — минимальный патч

```ts
setActiveClass: (classId) =>
  set((s) => patchActive(s, (p) => (
    p.activeClass === classId
      ? p
      : { ...p, activeClass: classId, adaptiveGood: 0 }
  ))),
```

Почему `adaptiveGood: 0`: адаптивное окно (сколько карточек добавлять)
набиралось на другой программе; сброс не влияет на опыт и награды.
`adaptiveCards` (сам потолок) не трогаем.

**Чего нельзя делать при смене класса:**

* `newProfile()` / пересоздание профиля;
* `resetProfile()`, `replaceAll()`, `restoreSnapshot()`;
* `touchDay()` / «новый день» — серия и `lastDay` не должны меняться;
* фильтрация или удаление `profile.words` / `profile.lessons`;
* обнуление `daily`, `weekly`, `shop`, `puzzle`, `achievements`, `days`.

### 6.3. Нормализация и совместимость

В `normalizeProfile()`:

```ts
const isClassId = (v: unknown): v is ClassId => v === 1 || v === 2 || v === 3 || v === 4;
// …
activeClass: isClassId(raw.activeClass) ? raw.activeClass : 2,
```

Строка должна стоять **после** `...raw`, иначе невалидное значение из файла
переживёт санитайзер.

* старые сохранения и старые выгрузки → класс 2, всё остальное как было;
* новые выгрузки в старой версии приложения просто игнорируют лишнее поле;
* `version: 1` в persist **не повышаем** — поле опционально на входе
  и нормализуется; поднимать версию значило бы рисковать миграцией
  без необходимости;
* `replaceAll` (импорт) уже прогоняет данные через `normalizePersisted`,
  отдельная миграция не нужна;
* при синхронизации двух копий `activeClass` приезжает вместе с профилем:
  это ожидаемо, как и остальные поля профиля;
* если в сборке ещё нет нужного класса (например, импорт из будущей версии
  с классом 4 в 0.27.0), селектор отрисовки берёт ближайший доступный класс
  (`AVAILABLE_CLASSES`), но **не перезаписывает** сохранённый `activeClass`:
  после обновления приложения ребёнок вернётся в свой класс.

### 6.4. Что происходит с наградами

| Поле профиля | Смена класса |
|---|---|
| `xp`, `gems`, `streak`, `lastDay`, `freezes` | не меняются |
| `achievements` | не меняются |
| `days`, `studySessions` | не меняются |
| `words` (прогресс по словам) | не меняется, все ключи остаются |
| `lessons` (уровни уроков) | не меняется, уроки другого класса просто не показаны |
| `daily`, `weekly` | не меняются; план дня не пересчитывается |
| `shop` (куплено, надето, тюнинг, музыка, звуки, мечты) | не меняется |
| `puzzle` (фрагменты, собранные, надетый костюм) | не меняется |
| `chestSkin`, `chestSkins` | не меняются |
| `activeClass` | **меняется** |
| `adaptiveGood` | сбрасывается в 0 |

Достижение «Знаток» (25 освоенных слов), рост БУКа (`GROWTH_STEPS = [12, 30, 60]`),
облик сундука за 30 слов и «Разбуди сундук» считаются по **всем** словам
профиля — класс на них не влияет. Перебалансировать пороги под 257 слов
**не нужно**: это сделало бы награды недостижимее для текущих детей.
Если когда-нибудь захочется — только отдельным решением и без отбора уже
открытого.

2. `npm run content:check` — ловит ударение, слоги, опасные буквы,
   падежи, мнемоники, опечатки в именах картинок.
3. `npm run test:content` — ловит связность уроков и классов.
4. Вычитка взрослым: значение, предложение, эмодзи, отсутствие ответа
   в предложении, естественность фразы.
5. Вторая вычитка по печатному словарику (наличие/написание/ударение).
6. Только после этого — релиз класса.

### 10.6. Картинки

* 94 существующие картинки остаются как есть.
* Для новых слов на старте — **эмодзи** (движок это уже поддерживает,
  `image` необязателен).
* Картинки добавляем позже батчами для конкретных существительных
  (овощи, животные, транспорт, профессии): `images-src/*.png` →
  `npm run images` → `public/words/*.webp` → имя в 10-м поле.
* Помнить про офлайн-кэш: `vite.config.ts` кладёт все `webp` в precache.
  257 картинок по ~5 КБ — около +0,8 МБ к установке; это допустимо,
  но лучше добавлять осознанно, а не «все сразу».

### 10.7. Чего не делаем без согласования

* озвучка и аудиофайлы слов (стоп-лист проекта);
* автоматическая транскрипция/озвучка;
* случайные или платные лутбоксы за слова;
* изменение экономики за прохождение класса.

## 15. Поправка 0.33.0: класс переехал в меню ☰

Пилюля класса стояла прямо над героем и занимала 54 px первого экрана
(`min-height: 44px` + `margin-bottom: 10px`) — почти столько же, сколько одна
карточка пути, на экране 320 × 568 это ≈9,5% высоты. Действие редкое:
класс меняется 1–3 раза в год, автоматически в конце класса («класс пройден»
→ «2 класс ▶») и вручную в «Родителям → Настройки».

Поэтому:

* **вход** — строка «🎓 2 класс» в меню ☰, в группе «про меня» рядом со
  «Сменить ученика»; открывает тот же лист `ClassSheet` («Какой класс
  учим?») с четырьмя карточками и прогрессом;
* **ориентация** — заголовок «Мой путь · 2 класс»: 0 px дополнительной
  высоты, строка и так есть на экране;
* **логика не изменилась**: `setActiveClass` по-прежнему меняет только
  программу, тост объясняет, что опыт, кристаллы и покупки на месте;
* **верхнюю строку не трогали**: четвёртый элемент в шапке — это ровно та
  перегрузка, из-за которой делался вариант B в 0.32.0.

Файлы: `src/ui/ClassSheet.tsx` (бывший `ClassPicker.tsx`, только лист),
`src/ui/screens/HomeScreen.tsx` (строка в меню + заголовок пути),
`src/styles/app.css` (удалены `.class-pill*`, добавлены `.home-path-class`,
`.menu-sep`), `tests/classes.test.ts`, `tests/smoke.test.tsx`.

Подпись кнопки в форме (0.34.0): на первом запуске — «Начать учиться 🚀»
(продолжать нечего), при добавлении второго ученика — «Создать ученика».
